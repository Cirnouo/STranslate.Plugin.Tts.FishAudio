# DD-049: Publish cancellable preview preparation before playback

**Status:** Current.

**Recorded:** 2026-10-20.

## Context

[DD-047](DD-047.md) downloads public sample audio before starting local output, and correctly publishes playing state only after output Play returns successfully. During the intervening metadata refresh, resource download and local preparation, the preview button continued to show its idle triangle. A second click already canceled pending work, but neither click changed the visible control, making the preview appear unresponsive. [Issue #6](https://github.com/Cirnouo/STranslate.Plugin.Tts.FishAudio/issues/6) reports this gap.

## Decision

Give the preview refresh coordinator a separate observable preparation publication. Publish the preparing Voice ID synchronously before the first request await, and clear it when the owning operation completes, fails, times out or is invalidated. Preserve the existing generation and cancellation-source ownership checks; only the current operation can clear preparation. A queued UI publication reads the current owner when it runs, so a canceled old completion cannot clear a newer spinner. Publish outside the operation lock.

Mirror preparation by Voice ID across the selected card and all matching visible search results, as for playback. Pending cancellation compares Voice ID rather than the entry-point object: a second click on the same voice cancels through either control without restarting the request. Keep the originating target identity for stale-response, result-removal and settings-write validation. Different voices replace pending work.

Show an indeterminate rotating ring and a center square during preparation. Keep that square enabled so the user can cancel. Successful output start removes the spinner and shows the existing actual output-position progress ring with its stop square. Idle shows the play triangle. Use five-locale tooltip and accessibility names for preview, preparing/cancel and stop states. Do not invent playback progress during network or decoder preparation.

## Consequences and limits

The first click now has immediate visible feedback while preserving intentional cancellation on the second click. Preparation is transient UI state, not persisted settings. Cancellation, selection/clear, removal of the originating search result, disposal and every failure path restore the appropriate idle state without affecting a newer operation.

This amends DD-047's state presentation and pending same-voice cancellation semantics. Its host HTTP download path, credential-free resource requests, shared fifteen-second deadline, eight-MiB bound, one-refresh budget, stale-result disposal and no-TTS preview rule remain in force. Playing state continues to require a successful local Play return. Automated tests use controlled request completions and player doubles; they do not establish physical sound or installed-host visual acceptance for the new spinner.
