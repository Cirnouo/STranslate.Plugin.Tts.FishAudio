# DD-063: Guard publication at the tag, host-version and draft-asset boundaries

**Status:** Current.

**Recorded:** 2026-10-23.

**Supersedes:** The publication protocol in [DD-028](../history/DD-028.md). The Windows build/test/package command and tag-equals-title constraints remain in force under this decision and DD-043.

## Context

The earlier workflow admitted broad `v*` tags, selected a changelog section and directly published through a release action. The repository now adopts the reference project's [release policy and publisher](https://github.com/Cirnouo/debugging-cdp-targets/tree/859808b66a7cf691f34a12344b209feee384c705/tooling/releases), retaining Fish Audio's Windows/WPF package rather than its Node/source-only distribution.

The latest published stable Fish release verified during adoption was v1.1.2, published 2026-10-01. It is the comparison baseline for the v1.2.0 changelog. Repairs to newly added streaming and UI work are part of the final descriptions of those capabilities. [v1.1.2 release](https://github.com/Cirnouo/STranslate.Plugin.Tts.FishAudio/releases/tag/v1.1.2)

There are two necessary adaptations. First, STranslate [v2.0.10's upgrade guard](https://github.com/STranslate/STranslate/blob/2a75118fe0fabc1135a619f4393eb3a8d936c5cd/src/STranslate/Core/PluginManager.cs) requires `System.Version.TryParse`. Its [marketplace](https://github.com/STranslate/STranslate/blob/2a75118fe0fabc1135a619f4393eb3a8d936c5cd/src/STranslate/ViewModels/Pages/PluginViewModel.cs) builds download tags from the manifest version. SDK metadata storing a string does not supply prerelease compatibility. Second, Fish distributes a `.spkg` asset, and published immutable releases cannot receive a replacement asset after publication.

## Decision

Keep one version owner in `plugin.json`, canonical three-component stable versions within Int32 component limits, and exact source/package/tag agreement. Reject prerelease/build/four-part/normalized aliases for installable publication. Do not strip a suffix, map it to a fourth component or silently change versions. A future channel needs separate host research.

Validate the new annotated push event and original tag object, peeled commit, checkout/event identity, required branch identity and current remote tag. Reuse full validation at that commit. Generate notes from exactly one matching real dated changelog section, preserving its body under English release scaffolding and optionally generated contributors. Use the latest published stable release as the comparison baseline.

Canonicalize the freshly built ZIP wrapper while preserving payload names/bytes, then verify and preserve the result under a validation-attempt artifact identity returned by the reusable workflow. This removes timestamp/order variation without transforming a downloaded or published asset. Create/resume a matching draft, upload and verify the exact validated package while draft, then publish and validate the returned identity/classification. A matching published rerun is a checked skip, not an overwrite. Use the built-in token and write permission only in publication. Failures preserve recoverable state and never delete releases/tags. Creating a real tag or Release requires explicit publication authorization.

## v1.2.0 amendment, 2026-11-11

The first stable publication under this protocol uses the frozen #43 baseline, which precedes the test infrastructure changes in #44 and #45. For the exact tag `v1.2.0`, require the exact tip of protected `refs/heads/release/v1.2.0` with sole parent `4bc15267a940040d4c485ff74ede45f1d61dc2ec`. Offline verification checks the remote-tracking branch. Publication checks the live branch alongside the tag before writing the draft, before inspecting draft assets, before finalization and before accepting a checked skip. Every other tag still requires ancestry on remote main. The full tagged-commit validation, package artifact and draft publication protocol applies to v1.2.0. [Release policy](../../policies/releases.md#tag-triggered-publication)

GitHub's push payload can report the peeled commit in `after`. Before pushing `v1.2.0`, pin the authorized local annotated tag object in the repository Actions variable `FISH_AUDIO_V120_TAG_OBJECT`. Admit the push only if `after` equals that object or the exact peeled `GITHUB_SHA`, and verify the pinned annotated object in Git and on GitHub at the existing checkpoints. The pin applies only to v1.2.0 and carries the public object SHA. [GitHub push payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push)

## Consequences and verification

Stable-only publication deliberately differs from the reference's prerelease support to preserve host upgrades and marketplace identity. Draft asset verification adds calls but protects immutable package delivery. Uncompressed canonical containers can be larger; their contents remain the validated build's payload. Release-tool regressions use fake Git/GitHub boundaries with no token, provider key, sound card or real release; ordinary dependency/audit/scanning jobs have separate service boundaries. Live tag/publication acceptance remains separate from offline protocol checks and must be reported honestly.

The [release policy](../../policies/releases.md) owns the procedure; [build and release specs](../../specs/build-and-release.md) own implemented behavior. DD-043 still owns build switches, and DD-023/DD-042 retain test/cleanup timing.
