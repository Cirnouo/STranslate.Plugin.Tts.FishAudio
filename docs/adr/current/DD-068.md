# DD-068: Gate complete CI coverage by the latest partition attempts

Status: accepted for the current Windows validation workflow.

## Current transition interpretation

The complete hybrid migration replaces the original five independent legacy jobs and separate foundation job with one full `Hybrid validation` Windows job. Its ordered plan retains the five fixed logical slots and complete framework tail, choosing each slot's current legacy or migrated framework owner from the immutable legacy reference, migration map and fresh discovery. An empty retired legacy partition is not an extra execution requirement. Producer and aggregate independently admit the raw complete plan; missing or failed owners cannot disappear through a workflow edit.

The always-scheduled `build-test-package` check, audit/commit prerequisites, both CodeQL checks and exact verified release-artifact chain remain required. Every new PR/main commit runs the full hybrid obligation. There is no affected selection, cross-commit reuse or complete-baseline claim. The original latest-actual-attempt, complete paginated history and authenticated cached-sibling time-witness rules below now apply to the complete hybrid job. A gate-only rerun may admit its unchanged complete actual attempt; an actual hybrid rerun repeats the complete plan. This temporary layout loses partition-job rerun granularity and retains the existing 90-minute limit. Actual final Windows CI duration and rerun behavior must still be observed; local timing and source controls alone cannot establish them.

Raw evidence retains original absolute request/process paths. Only matching checkout, temp and executable roots are supported: the aggregate computes a fresh fixed bundle destination from trusted runner/event context, validates its selected owner and complete inventory, copies raw bytes there, rebuilds current verifiers and independently readmits all owners. A different layout fails closed without rewriting JSON. This is a bounded transport contract, not a portability claim or authorization to change remote required-check rules. The [build specification](../../specs/build-and-release.md#validation-and-publication) describes the active workflow; the independent partition design below remains the rationale and earlier layout.

## Context

One combined build/test job required replaying all native regression work after an isolated failure. Independent jobs permit targeted recovery, but a matrix result alone does not prove that the current catalog ran completely. Same-run reruns can retain successful sibling jobs from earlier attempts; requiring one common attempt would force needless reruns, while selecting the latest successful artifact could conceal a newer failure.

## Decision

Run the five existing process partitions on independent Windows runners, each checking out the exact validation SHA and rebuilding with the fixed SDK. Limit matrix concurrency to four and disable fail-fast. Every new PR/main validation commit runs all partitions. Local affected selection and old binaries never skip a CI partition.

Keep the existing build-test-package check as an always-scheduled aggregate. Require successful audit, commit and matrix dependencies, then validate complete report evidence against the freshly built exact current catalog. Bind repository, workflow run, attempt, producer job, partition, clean source and build identity. Record runtime observations without imposing a new cross-attempt runtime-equality restriction. CodeQL retains its independent required checks.

Within the same SHA and workflow run, choose each partition's highest actual job/artifact attempt before reading report contents. Verify a complete paginated jobs snapshot and an exactly matching successful job/report. Missing, corrupt, failed, cancelled, skipped or incomplete newest evidence cannot borrow an older success. Old failed evidence remains retained and does not poison a later complete repair. Never join casewise prefixes from different attempts into full coverage. A gate-only rerun can reuse the five latest complete sibling reports.

An Actions rerun can expose a new job ID and advertised run attempt for a cached sibling whose execution did not run again. Authenticate every attempt's UTC start through the attempt-specific API. Resolve only complete successful records that finished strictly before their advertised attempt to a unique earlier actual execution with the same controlled name, head, runner, timestamps and full ordered step metadata. Ignore API view identifiers and runner-group fields that can change during copying. Retain actual newer failed or unfinished records at their advertised attempt. Incomplete, changed, overlapping or ambiguous metadata fails closed; artifact attempts are never rewritten or used to guess reuse. This conservative recognition follows observed API evidence, not a documented guarantee that job attempts identify fresh executions.

CI validation is stricter than the compatible local recovery reader. Require physical identity/result fields and the parent generation store, including initial, canonical-referenced and highest committed records, plus coherent final child canonical/snapshot evidence. Compare shared ordered results while retaining parent-only diagnostics; successful parents may have no child-exit-code field. Valid stale canonical outcomes can resolve to the authenticated complete latest generation. Include CI ownership in immutable report metadata; fake internal calls and old local reports keep null CI context.

After process exit, preserve exact evidence bytes in separate immutable attempt artifacts. Compact only intermediate generations, retain required path layout and highest committed filenames, and never manufacture missing projections or choose the newest parseable older file. Exclude private request arguments and unfinished temporary writes. The aggregate reads Actions metadata with read-only capability, including through the reusable release caller. After complete coverage succeeds, perform the final fresh package build/inspection and continue the existing exact publication-artifact output chain.

## Consequences

Same-commit failures can be recovered at job granularity while new commits retain complete coverage. Five fresh builds and a small report verifier add predictable overhead in exchange for independent execution and explicit evidence. Attempt selection, field/default handling, generation compaction and registry matching require offline negative fixtures, and cached-sibling artifact reuse needs a real selective-rerun integration check. No release tag, publication, bypass or branch-rule change is authorized by this decision.

The [build specification](../../specs/build-and-release.md#validation-and-publication), [verification policy](../../policies/verification.md) and [repository governance](../../policies/repository-governance.md) own current implementation and maintenance behavior.
