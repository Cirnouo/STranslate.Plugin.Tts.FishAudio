# DD-061: Keep four device buffers without increasing each refill block

**Status:** Current.

**Recorded:** 2026-10-23.

**Amends:** The device-queue margin in [DD-052](DD-052.md); its software startup, bounded ring and drain rules remain active.

## Context

Intermittent electrical noise was reported during PCM streaming. A live capture preserved every upstream PCM byte through the production provider and inserted silence only at the utterance tail. That capture alone did not reproduce or explain the audible complaint.

A controlled offline comparison replayed the same saved fifteen-second source through the production decoder, ring, player and output adapter, with the same source-availability schedule. The user reported the symptom with the existing 100 ms/two-buffer output and clean playback with 200 ms/four buffers. The first run also had repeated long provider refill gaps, while the second retained steadier refills. Both delivered identical real PCM without software-ring padding during speech. This supports changing device-queue margin rather than modifying generated samples.

## Decision

Use NAudio `WaveOutEvent` with desired latency 200 ms and four buffers. Each device buffer remains approximately 50 ms. Keep the existing context-free construction, cancellation, device-position tracking, final-real-sample drain and cleanup ownership.

Do not change the five-second software ring, 250 ms/100 ms startup conditions, native WebSocket protocol, lazy text prefix, tail gate, sample rate, codec, volume or source PCM. Do not introduce fades, noise filtering or automatic retries as part of this change.

## Consequences and verification

The requested device queue has an additional nominal 100 ms of margin. This can add output queuing delay; it is separate from the first-prefix scan and does not grow with total input length. Desired latency is a device configuration request, not a measured acoustic latency guarantee.

The same-source listening comparison and refill observations support this mitigation on the exercised device. They do not prove a universal driver mechanism or guarantee absence of every audible artifact. Verify exact source/provider bytes, speech-time padding, real-tail device progress, cleanup and the user's listening report separately. Keep failed and successful comparisons distinguishable.
