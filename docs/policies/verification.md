# Verification policy

Choose verification that exercises the changed contract. The repository uses an executable regression runner, not a test-discovery framework: new regression scenarios must be invoked by its Program entry point. Keep normal tests deterministic and offline; do not make a credential or provider availability a prerequisite for CI.

## Incremental verification and failure recovery

After a failure, diagnose and fix the failing contract, then rerun only checks that can be affected by the final change. Before execution, record the changed code or fixture, its callers and shared dependencies, the selected runner entries, prior results that remain applicable, and coverage that has not run. Include adjacent compatibility and lifecycle checks when the dependency trace requires them. Changes to shared dispatch, theme, layout, storage, cancellation or test infrastructure can affect several suites; justify that scope from the dependency, rather than selecting either one assertion or the entire runner by habit.

Preserve successful results for unchanged contracts and dependencies, together with their source/tree identity, configuration, invocation and raw outcome. Reassess applicability after each edit. A documentation-only correction does not invalidate unrelated native matrices. Build changed code and run the selected entries from the resulting fresh outputs; a build needed for compilation or packaging does not itself require executing the whole runner. Reuse existing selectors where possible. A new focused selector must call the original scenario with its assertions, ownership, cleanup and deadlines intact and must not remove it from normal registration.

Keep a failed whole command recorded as failed. A passing focused rerun establishes only its stated scope; it neither converts that earlier command into a pass nor covers scenarios that never ran. Track affected reruns, reusable prior coverage and outstanding coverage separately. Preserve evidence before cleanup, and inspect a distributable built from the final intended sources independently of whether regressions were selected or combined.

The ordinary local pre-push check builds and inspects the current Release package and runs the affected regression groups. Use the explicit source/shared-dependency recommendation, include working-tree changes, and expand unknown dependencies conservatively. A failed or interrupted run leaves not-run coverage outstanding; recovery includes that coverage and groups affected by the final fix. Every new PR/main validation commit still runs the complete CI regression set. Local selection never authorizes skipping mandatory CI checks or reusing an earlier commit's green status for a new commit.

The executable runner supports stable group and case selection, metadata-only listing, and an incremental run report. Treat a continuous same-owner workflow as one replayable case; phases within that workflow are diagnostics, not independent fixtures. Preserve the original scenario delegates and assertions when adding selectors. Unknown selectors and empty matches fail rather than silently running all or reporting zero-case success. Reports identify source/configuration, selected cases, actual outcomes and not-run cases; a focused pass never rewrites a previous failed report. Preserve the requested JSON and its immutable generation sidecar together. Use the runner's report reader for recovery so a temporarily stale projection cannot hide newer failed/not-run coverage.

Do not automatically restart the full local test command after an individual failure, a focused fix or a bookkeeping change. Use one bounded investigation of the unresolved failure and expand verification only for a concrete dependency or remaining coverage risk. When scoped local recovery is requested, keep local reruns scoped and explain any need for a broader run before executing it. Existing mandatory CI checks remain governed by repository governance; report their actual scope separately and do not silently weaken or bypass them. A final report must distinguish a full passing CI run from the collection of scoped local results.

## Test ownership and budget preflight

Before designing or modifying a test, trace its entire dispatched callback through called helpers, nested callbacks and loops. Enumerate construction, binding/layout, input, transitions, assertions and cleanup; the shared regression execution deadline covers that complete callback, not each operation or the top-level helper name. Count every repeated case and native action before choosing its grouping and budget.

Separate independent rendered/native and non-STA asynchronous workflows into independently owned actions. When a regression requires one source/object to retain state across a sequence, preserve that same-owner chain. Inspect all callback descendants and cleanup before changing ownership. An aggregate catalog entry can contain many separately guarded actions; do not apply an action deadline to that entire entry. Multiplying action counts by protective limits does not predict runtime and is not a maintenance requirement. Use measured per-case and phase timings to identify expensive work.

Use the [regression process profile](../specs/build-and-release.md#regression-process-isolation) for pure execution protection: warn after twenty seconds and keep waiting for the same task; latch hard failure after 120 seconds measured from before queueing through actual callback cleanup. Child-process and Dispatcher startup each have a separate 120-second guard. Nested dispatch, phase changes and cleanup do not renew the root deadline. At hard expiry, diagnostics share at most ten seconds including scheduling, observation and writing, after which the parent outside the STA terminates the polluted child. Already completed results remain evidence; unexecuted cases remain not-run and other selected partitions continue. Never continue dispatching on the polluted STA or automatically retry, replace or cancel the original action. A late completion remains failed. Preserve the original failure when reporting or cleanup also fails; blocked output may be incomplete and cannot acquire another allowance. Provider deadlines, fake-clock stimuli, native tooltip idle/readability limits and functional dwell/error/buffer assertions retain their own meanings.

- Use fake network/storage/audio boundaries for request shape, cancellation, timeouts, stale results and failure cleanup. Use fixed local fixtures when real decoding is relevant.
- Test asynchronous preview ownership separately from shared Voice ID state: removing the originating card must invalidate its pending work even when another card has the same ID; accepted local playback instead belongs to the controller, and local collection persistence/rebuild must preserve selection until an explicit Apply.
- Run WPF fixtures that share process-global theme resources on one STA Dispatcher with a dispatcher synchronization context; preserve real background-thread completion and command-listener checks.
- For responsive settings changes, exercise the compiled themed controls at narrow and normal widths. Compare icon, header and content geometry with existing native cards, including visible validation text; correct header alignment alone does not establish content alignment. Apply pending binding/layout and responsive visual-state work before measuring.
- For documentation moves, validate local targets, preserved anchors and the existing repository assertions affected by the move. Do not add large sets of source/text assertions that merely mirror the documents.
- For behavioral changes, test meaningful before/after cases and affected compatibility paths. Repeat or broaden checks when the final changes, a failure or an unresolved risk justify it.
- Build/package validation must inspect the package produced by the current sources and configuration, including required dependencies and resource files. A leftover package is not evidence of a successful current build.
- For plugin class libraries, verify private runtime dependencies inside the distributable, not only in the test project's output. The test runner can resolve a NuGet assembly that the package omits. Copy resolved private runtime assets deliberately; do not accidentally bundle a second host contract or UI framework to repair a missing dependency. Missing required runtime files must fail the build rather than emit a warning.
- Validate the final state intended for review and commit. If code, tests, a spec, resources or CHANGELOG changes after a successful check, rerun the affected checks before claiming final verification. Report exactly what was run and any remaining limits.

On Windows with .NET 10, the standard combined release verification is `./build.ps1 -Release -Clean -Test`. Debug is the default; `-Test` runs regressions and `-Clean` cleans intermediates after the operation. See [build and release behavior](../specs/build-and-release.md) for the implementation contract.

Published release-contract checks protect the content and ordering of historical version sections. They must not require the Unreleased section to stay empty or demand that an old architecture remain the current implementation forever. Adapt location assertions when a document is moved while retaining its historical meaning. The [release policy](releases.md) owns baseline/category selection, notes and publication. Keep parser, tag-admission and draft/asset/final-state failure tests deterministic with fake Git/GitHub boundaries; never publish a real release as a test of those fixtures.

Distinguish a completed command from a passing check, and a passing offline check from live service/audio success. A final report states what changed, the checks and final file state they cover, failures or skipped work, and material limitations. The [API evidence policy](api-evidence.md) governs all real network or synthesis claims.

## Native presentation and asynchronous evidence

Use these common rules together with the affected [settings](../specs/settings-and-model-policy.md), [voice and popup](../specs/voice-browsing-and-preview.md) or [lifecycle](../specs/architecture-and-lifecycle.md) contract. Those specifications own domain scenarios and historical oracles; the catalog owns current case IDs and order. Do not duplicate per-suite action ledgers or estimate runtime by multiplying actions by their protective limits.

- Keep real compiled controls, independent native peers and source ownership where the assertion depends on them. Exercise supported themes, widths and locales where they change resources or geometry. Materialize lazy native TextBoxView parts before injecting visual-root DPI and assert both scales; bitmap resolution alone is not actual WPF DPI or OS scale. Inspect the text viewport, carets, glyphs, neighboring content, validation space and responsive layout as well as outer bounds. Apply the fixture's existing semantic binding/layout readiness before observing it, without extra idle pumps, polling, retries or warmups. Preserve first-use order: card ink before numeric DPI geometry, and Search before native keyboard state. Cold first use and later warmed execution are different measurements.
- Separate geometry, behavior and pure logic only when the dimensions have independent risk evidence. Retain all static geometry boundaries and each historical oracle, document where every removed matrix assertion continues to execute, and measure construction as well as layout costs. A continuous mutation/restoration, input, persisted-reopen or lifecycle chain remains on its original object/source owner. Do not turn phases into replayable cases or reuse a polluted fixture. Keep native tooltip open/readiness/close and original tooltip restoration with their owning input chain. Preserve selected/active card pairs, compiled binding expressions and equivalent cleanup.
- Use independent observations for typography and raster claims. Native drawing bounds, exact glyph outlines and physical raster support measure different things. Declare the classifier, fixed crop, sampling phase and displacement sensitivity; retain the original pre-fix oracle and distinguish historical reference strips from current product positions. Actual paint and opaque isolation have separate purposes. Do not move individual glyphs, change production snapping or weaken a bound to obtain a pass. Headless palette overrides must be explicit, local and restored. The settings and voice specifications own the exact numeric, action-ink and short-author bounds.
- Synchronize on the publication or state actually asserted. A device Play counter, a pending timer or global Dispatcher idleness need not mean that the relevant notification or progress baseline exists. Register causal signals before triggering work, detach in finally, and preserve exact fake-clock threshold/deadline assertions. Hover qualification uses the monotonic fake clock and checks both sides of its threshold; arbitrary sleeps cannot establish it. Test background-thread command listeners and pre-drain retirement state where those are the contract. An owned timeout must come from the original faulted task with the same exception identity; the execution guard must not satisfy that assertion. Preserve the original failure through reporting and cleanup.
- Label fixture evidence precisely. Hidden native sources, injected root DPI, forced theme states, declared headless palettes and synchronous native keyboard-table transactions do not establish installed-host appearance, OS-scale changes, physical input, audible output or the cause of a historical timeout. Keyboard fixtures reject unsupported contexts without forcing foreground/device state; restore the complete captured table, retain the existing controlled-key postconditions and publish only fixed safe differences, never raw key tables or user text. Passing isolated diagnostics do not explain an earlier warmed full-run failure.
