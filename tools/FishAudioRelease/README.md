# Fish Audio release tooling

This BCL-only .NET 10 console tool implements the [release policy](../../docs/policies/releases.md). It has no Fish Audio API dependency, reads no host profile and never changes a version, tag or changelog.

Run the deterministic offline protocol tests:

```powershell
dotnet run --project tools/FishAudioRelease -c Release -- --self-test
```

The self-test uses an in-memory Git/GitHub boundary and a fake HTTP message handler. It never reads `GITHUB_TOKEN`, creates Git commits, calls GitHub or publishes a release. Coverage includes canonical stable versions, fenced Markdown and duplicate/date/empty sections, new-tag event admission, source/package manifest agreement, draft upload/download/finalization order, draft resume, published-package skip, digest mismatch, remote tag or v1.2.0 branch movement at write boundaries, local tag rejection, injected upload/download/publication failures, and credential isolation on asset redirects.

`--canonicalize-package` operates offline on the freshly built root package and verifies its manifest after transformation. It never rebuilds or changes payload bytes. The publisher downloads the completed validation artifact and never canonicalizes or rebuilds it.

`--verify` requires the GitHub tag-push environment and event file, checks the exact annotated tag, original pushed tag object, peeled commit, checkout HEAD, required branch identity, dated changelog and current root `.spkg`. It makes no HTTP requests. CI runs this after the complete Windows Release build and offline tests, then preserves that exact package as a workflow artifact. Before release verification, CI canonicalizes only the ZIP container: ordinal entry order, fixed timestamp/attributes and stored payload bytes. Entry names and uncompressed contents are preserved; duplicate/case-colliding or unsafe names fail. This removes ZIP metadata variation across reruns while any changed DLL/resource still changes the verified package bytes. Each successful validation attempt exposes its unique artifact name through the reusable workflow output; a publication-only rerun consumes that original successful validation output.

`--publish` is exclusively the publication job entry point. It accepts only the built-in `GITHUB_TOKEN` environment variable and a newly created, nondeleted, nonforced tag push. It revalidates the downloaded verified package, constructs curated release notes using GitHub's latest stable release and optional contributor bullets, creates/resumes a matching draft, uploads and downloads the asset to verify its SHA256, rechecks the remote annotated tag, then publishes the immutable stable release. It never deletes a tag/release, replaces an asset or repairs a published release. A matching published release skips only after package and remote identity verification. Failure leaves the draft for inspection and a safe rerun.

For `v1.2.0`, both modes require the exact `refs/remotes/origin/release/v1.2.0` tip and sole parent `4bc15267a940040d4c485ff74ede45f1d61dc2ec`. Publication also checks the live `refs/heads/release/v1.2.0` alongside the annotated tag before the draft write, after verifying the draft and before inspecting its assets, before the final write, and after verifying package bytes before accepting a published skip. Every other stable tag must be reachable from `refs/remotes/origin/main`. [Release policy](../../docs/policies/releases.md#tag-triggered-publication)

Before pushing the annotated `v1.2.0` tag, record the public SHA from `git rev-parse --verify refs/tags/v1.2.0` in the repository Actions variable `FISH_AUDIO_V120_TAG_OBJECT`. Both modes require this value for v1.2.0. Its event `after` may be the pinned object or the peeled `GITHUB_SHA`; local and remote annotated objects must match the pin. Other tags continue using `after` as the expected tag object.

Only exact canonical `vM.m.p` stable tags with Int32 components are accepted. STranslate 2.0.10 upgrades use `System.Version`, and the marketplace constructs the download tag from the package manifest. Prerelease/build suffixes, leading zeros, fourth components and suffix-stripping mappings are deliberately rejected. `plugin.json` remains the sole package version owner. The SDK's string metadata type does not establish host prerelease compatibility.

The adapter uses fixed GitHub API/upload origins and disables automatic redirects. GitHub asset downloads may return HTTP 302; the tool follows only an HTTPS `release-assets.githubusercontent.com` location, without forwarding authorization. Signed URLs, token values and API response bodies are withheld from diagnostics. The HTTP protocol behavior follows the [GitHub release-asset API](https://docs.github.com/en/rest/releases/assets).

Workflow action revisions are immutable pins. The checkout/upload/CodeQL pins follow the reviewed reference workflow at `859808b66a7cf691f34a12344b209feee384c705`; setup-dotnet v5.3.0 and download-artifact v7 were resolved from their official repositories. CodeQL C# uses manual Windows .NET 10 compilation of all four maintained projects, following [CodeQL compiled-language build guidance](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages) and its [.NET 10 support matrix](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/). Separate CodeQL checks need successful main/PR scans and finding review before becoming required governance checks.
